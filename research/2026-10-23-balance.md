# Can a key's balance be read from the API? — 2026-10-23

Short answer: **no, not with a model API key.** Balance is a console-only number.

Probe: `probe-balance.mjs` (re-runnable, ¥0 — every call is a rejection or
metadata). Raw outcomes: `evidence-2026-10-23-balance.json`.

## What was checked

1. **The documented spec.** `docs.bigmodel.cn/openapi/openapi.json` has 106
   paths. Grepped for `account|balance|biz|finance|bill|quota|credit|resource|`
   `package|usage|cost` — the only hit is
   `/llm-application/open/knowledge/capacity`, which is knowledge-base capacity.
   There is no account, wallet or invoice surface in the published API.
2. **Seventeen plausible console paths** under `/api/biz/*` and friends.
3. **Auth shapes** on whatever existed: `Authorization: Bearer <key>`,
   `Authorization: <key>` (no scheme), `X-Api-Key`, and no header at all.
4. **Response headers** of an ordinary 2xx chat call, for a balance/quota leak.

## What was found

Four distinct outcomes, and the difference between them is the whole answer:

| outcome | meaning |
|---|---|
| `200 {"code":404,"msg":"接口不存在: /customer/…"}` | `/api/biz/*` **is** a real router, that method name does not exist (note: in-band 404 with HTTP 200 — the same habit as the auth envelope) |
| plain `404 {"status":404,…}` | no such route (`/api/finance/…`, `/api/paas/v4/account/…`) |
| `200 {"code":1001,"msg":"Header中未收到Authorization参数…"}` | an endpoint that exists and wants auth |
| **`403 APIKey not allow access: /biz/customer/getCustomerInfo`** | **exists, refused for this key class** |

So exactly one account endpoint is reachable at all —
`GET /api/biz/customer/getCustomerInfo` — and it answers a plain-text
`403 APIKey not allow access` for a funded key (`KEY7`), for a zero-balance key
(`KEY1`), and under all three header shapes. The refusal is an allow-list
decision about *key class*, not about balance, so it cannot be worked around by
having money on the account or by using another key.

Ordinary calls leak nothing either: the only headers are `date`, `content-type`,
`content-length`, `set-cookie` (an `acw_tc` anti-crawler cookie), `ga-traceid`,
`x-log-id`, `x-request-id`, `alt-svc`. No `X-RateLimit-*`, no quota, no balance.

## Consequences for this plugin

- The plugin cannot display a balance, and should not pretend to. What it *can*
  say is the runtime truth, which it already does: an empty balance arrives as
  `429/1113` (`insufficient_quota` on the Responses surface) and is rewritten
  into a non-retryable message with the top-up link
  (`https://bigmodel.cn/finance`, `BILLING_URL` in `errors.ts`).
- **Spend ≠ balance.** pi computes per-turn and per-session cost from the
  catalog prices, and that number is real; the remaining balance is not derivable
  from it in either direction, because there is no total to subtract from.
- A `/bigmodel` "balance: …" line would therefore have to say either "unknown,
  console only" or "empty as of the last refusal at HH:MM" — thin enough that it
  was not added. The billing hint already carries the actionable half.

## Notes for whoever repeats this

- The endpoint-name oracle is real and cheap: an existing-but-forbidden method
  answers `403 APIKey not allow access`, an unknown one answers the in-band
  `404 接口不存在`, a wrong router answers plain `404`. If BigModel ever opens the
  console API to keys, this probe will find it by flipping one verdict.
- Do not read a "helpful" verdict from a probe that greps for a word: the first
  version of this script matched `balance` inside the in-band 404's *echoed
  request path* and cheerfully reported that it had found a balance API. The
  check now requires a 2xx body that is not an error envelope and an actual
  numeric amount field.
