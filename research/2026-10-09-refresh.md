## What changed in the provider since 2026-09-24

1. **GLM-4.7 and GLM-4.5V stopped being forced thinkers.** `thinking:{type:"disabled"}`
   now returns 200 *and* is honoured: a 64-token answer to "12*13" came back as
   `content: "156"` with `completion_tokens_details.reasoning_tokens: 0`, while
   `enabled` spent all 64 tokens in `reasoning_content`. Catalog reclassified to
   `dynamic`, so pi offers "off" again. `thinking.md` still calls both 强制思考;
   `thinking-mode.md` documents 轮级思考 (turn-level thinking) as a GLM-4.7
   feature — the two pages contradict each other, the gateway agrees with the
   second one.
2. **Context overflow is 400/1261 `Prompt exceeds max length`.** Reproduced for
   free (200K-token prompt into a 128K-window free model; rejections are not
   billed). pi-ai 1.1.0 already matches that exact string as the "z.ai CN
   endpoint token overflow" pattern, so compaction works even without our
   rewrite; we still normalize the documented Chinese form (`Prompt 超长`),
   which pi does not match.
3. **Empty balance arrives as HTTP 429 code 1113** (`余额不足或无可用资源包,请充值。`).
   pi's retry classifier is text-based and `429` is in its retryable list, so a
   broke key spun ~16 s in print mode before failing. Now rewritten into an
   actionable message carrying a deny-list tag (`[billing 1113]`), which
   `isRetryableAssistantError` checks *first*: the same scenario now fails in
   1.1 s. Same treatment for the quota-window codes (1308/1310/1316–1321) and
   the plan codes (1309/1311/1314/1315); genuine throttles (1302/1305/1313) are
   left retryable.
4. **The 401 wording is `身份验证失败` (code 1000)**, not the
   `令牌已过期或验证不正确` (1003) this plugin used to quote. Both are matched now,
   plus 1001/1005, and the matcher no longer depends on pi prefixing the status.
5. **Image limits are documented**: ≤5 MB per image, ≤6000×6000 px,
   jpg/png/jpeg, ≤50 images per request for the 5.3-Flash / 5V-Turbo / 4.6V /
   4.5V families (`openapi.json` → `VisionMultimodalContentItem`). The old
   `IMAGE_LIMITS_BY_ID` carried z.ai's numbers (2000×2000, 4 718 592) and was
   **dead code** — never imported, so pi always applied its own default profile.
   Now published as `Model.inputLimits`.
6. **Two sibling protocols appeared** and are documented in the README's
   "Протоколы и поверхности": Response API on `https://open.bigmodel.cn/api/v1/responses`
   (probed: `400 {"code":"model_not_found"}` for an impossible id) and an
   Anthropic-compatible surface on `https://open.bigmodel.cn/api/anthropic/v1/messages`
   (probed: `400 {"code":"1211","message":"[1211][模型不存在…][request_id]"}`).
   Neither is wired; both are recorded as "exists, deliberately not added".
7. **`glm-4.5` and `glm-4.5v` vanished from the docs' model enums** (and from
   `model-overview`), yet both still answer 200, echo their own id in `model`
   (no silent rerouting), and `GET /models` still lists `glm-4.5`. Kept in the
   catalog with `¥0` + `priceNote`, since the public price page only offers
   private instances for them. `glm-4.5-flash` is marked 即将下线 with no date.
8. **No new models.** The release log's newest entry is GLM-5.3-Flash
   (2026-08-26); `GET /models` returns the same 11 ids as in September.

## What the gateway accepts but does not honour

A methodological finding that invalidates a probing habit: **this gateway
silently accepts fields that do nothing.** Measured 200 for all of these:

- `reasoning_effort` on `glm-5.1`, `glm-4.7`, `glm-5v-turbo`, `glm-4.7-flash`,
  `glm-4.5-flash` (docs: GLM-5.2+ only) — and the effort *is* enforced where it
  matters: `glm-5.3` + `medium` → 400/1210;
- `store: false`, `prompt_cache_key`, `prompt_cache_retention: "24h"` (none of
  them in `ChatCompletionTextRequest`);
- `tool_stream: true` on `glm-4.5-flash` and `glm-4-flash-250414`, which the docs
  do not list as supporting it;
- `thinking:{type:"disabled"}` on `glm-4.1v-thinking-flash/flashx`, which then
  think anyway (inside `content`, as a `<think>` block, with no
  `reasoning_content` and no `reasoning_tokens`).

So "answered 200" is not evidence of support on this endpoint. Every such flag
in `catalog.ts`/`models.ts` now cites the specification, and the live probes
assert *behaviour* (reasoning_tokens, cached_tokens) rather than status codes
where the distinction matters.

## Cache, measured

Implicit, no request fields, hits in `usage.prompt_tokens_details.cached_tokens`
(docs `capabilities/cache.md`; storage 限时免费 → `cacheWrite: 0`; hit priced at
the published 缓存命中 rate, ~25–50 % of input).

Same ~2.3K-token prefix, repeated:

| model | gap | result |
|---|---|---|
| `glm-4.5-flash` (free) | 4 s | `cached=4`, then `1508/1510`, then `1508/1510` |
| `glm-5.3-flash` | 6 s, 25 s | `cached=0` three times |
| `glm-4.7` | ~3 min after the first pair | `cached=2304/2329`, repeat `2304` |
| `glm-4.7` (2× prefix) | 30 s | `2304` (older half hit), then `4608/4648` |
| `glm-4.5-flash` (live smoke, ~850-token prefix) | 8 s | `[4, 848, 848]` |

Reading: population is asynchronous and takes seconds on the free tier and
one-to-three minutes on the paid models; it is not sharded-away or lost, which is
what the September note assumed. Hits are near-total on the shared prefix, not
partial.

Consequences in code:

- `promptCache` stays **unset**. pi reads it only to compute a warmer TTL
  (`getPromptCacheTtlMs` → `CacheWarmer`); with no TTL the warmer stops with
  "cache lifetime unavailable", so the plugin never triggers extra billed
  warm-up requests even though this machine runs `cacheWarming: "idle"`.
  Inventing a TTL would have started spending money on a cache we cannot
  schedule. Asserted by a test.
- pi's `showCacheMissNotices` uses a hard-coded 5-minute Anthropic TTL and a
  20K-token/$0.10 threshold, so BigModel sessions will show cache-miss notices
  after idle gaps. Expected, not a misconfiguration — documented in the README.
- Accounting verified through the real adapter (`test/wire-format.test.ts`):
  a recorded body with `prompt_tokens: 2329, cached_tokens: 2304` yields
  `usage.input = 25`, `usage.cacheRead = 2304`, and `cost.cacheRead` at the
  catalog's ¥0.6 rate for glm-4.7. Tier selection uses `input + cacheRead`
  (pi-ai `calculateCost`), which matches BigModel's 「输入长度 ≥32K」 band being
  about prompt length, not about the freshly billed part — also asserted.
- Preserved thinking lines up: pi sends `clear_thinking:false` and replays
  `reasoning_content` for same-model transcripts (`thinkingSignature` +
  `transform-messages.js` `isSameModel`), which is exactly what
  `thinking-mode.md` requires for that mode, and which the docs say improves
  cache hit rate.

## pi 1.1.0

- `npm run check`: typecheck clean, 92/92 offline tests (was 53).
- `npm run live` with a funded key: 36/36, ~127 s, ≈¥0.05.
- `detectCompat` now recognises `open.bigmodel.cn` as z.ai
  (`api/openai-completions.js:1227`), so `thinkingFormat`, `maxTokensField`,
  `supportsStore` and `supportsDeveloperRole` are auto-correct; the explicit

  `supportsStrictMode: true` is a *permission* for pi's own constrained tools
  (`read`, `strict:"prefer"`) rather than something sent on every request.
- Runtime checks in a clean `HOME` with the plugin loaded via `-e`: model listing
  (24 ids), a tool-using turn on a free model, `glm-4.7:off`, `glm-5.3:off`
  (clamps to `low`, no 1210), the 401 path and the 1113 path in print mode.
- pi ships a built-in `zai-coding-cn` provider on
  `https://open.bigmodel.cn/api/coding/paas/v4` (GLM Coding Plan). Different
  endpoint, different billing, no id collision with `bigmodel`; its generated
  catalog independently confirms the compat flags this plugin chose
  (`thinkingFormat: zai`, `zaiToolStream`, `supportsStrictMode`, `max_tokens`).

## Thinking: the decisive measurement

GLM-4.7, "12*13", `max_output_tokens` 400, reasoning tokens per call:

| request | reasoning_tokens |
|---|---|
| Responses, `reasoning.effort: "none"` | 118 / 114 |
| Responses, `"minimal"` | 74 |
| Responses, `"low"` | 114 |
| Responses, `"medium"` | 113 |
| Responses, `"high"` | 72 |
| Responses, `"max"` | 73 |
| Responses, `"xhigh"` | 56 |
| Responses, no `reasoning` field | 105 |
| Responses, undocumented `thinking:{type:"disabled"}` | 114 |
| Responses, `do_sample:false` + `effort:"none"` | 93 |
| **completions, `thinking:{type:"disabled"}`** | **0** |
| completions, `thinking:{type:"enabled"}` | 92 |

So on Responses the effort knob is noise for GLM-4.7 and nothing disables
thinking; on completions `disabled` genuinely zeroes it. Free models behave the
same way (`glm-4.7-flash`: none 125, low 276). GLM-5.2 on Responses: none 98,
minimal 120, low 2, max 82 — again no ordering. GLM-5.3 validates the effort
enum on both surfaces (`none`/`minimal`/`medium`/`xhigh` → 400
「该模型始终思考，不支持关闭思考；请使用 low、high 或 max。」).

Design consequence: on Responses every thinking-capable model gets
`RESPONSES_EFFORT` with `off: null`, so pi does not offer a switch the gateway
ignores; `clampThinkingLevel(model, "off")` walks up to `minimal`. Users who need
a real off switch set `BIGMODEL_PROTOCOL=completions`.

## In-band HTTP-200 auth failure

With a revoked key, a garbage key and with no `Authorization` header at all, the
Responses endpoint answers:

```
HTTP 200 application/json
{"code":1000,"msg":"身份验证失败。","success":false}
{"code":1001,"msg":"Header中未收到Authorization参数，无法进行身份验证。","success":false}
```

Through pi's adapter (which always streams) that surfaces as
`"OpenAI Responses stream ended before a terminal response event"` — a string in
pi's RETRYABLE list, so a dead key retries for the whole budget and the user is
never told the key is the problem. Fixed with a `fetch` wrapper
(`withGatewayErrorRemediation`) that re-emits such a body as
`401 {"error":{"code":"1000","message":"身份验证失败。"}}`, which the existing
auth rewrite already handles. Narrow by construction: status 200 + JSON content
type + `{code:number, msg:string, success:false}`, body read via `clone()`.
Live-tested end to end with a real garbage key.

Note `statusText` cannot carry the Chinese message: undici rejects non-Latin-1
reason phrases, so the remediated Response omits it.

## Image wire shape — a false negative, and how it was caught

Round 1/2 said "the Responses surface rejects base64 data URLs" (`400
invalid_request 图片输入格式/解析错误`) and "the completions-style `image_url:{url}`
object works". Both halves were wrong, and the control that exposed it was the
skill's rule: re-probe a surprising negative with a known-good input.

- the fixture PNGs were hand-assembled and invalid (`Buffer.from(Array(8).fill(Buffer.from([255,0,0])))`
  produces a buffer of Buffers, not pixels) — the 400 was about *our* bytes;
- with a correctly encoded 16×16 four-colour PNG, `image_url` **as a string data
  URL** (pi's own shape, including `detail:"auto"`) is read correctly: the model
  answers "top left is red, top right is blue, bottom left is green, bottom right
  is yellow", `input_tokens` 34-40;
- `image_url: {url: "data:…"}` is accepted with HTTP 200 and the image is
  **silently dropped**: `input_tokens` 16 (text only) and the model describes
  "a blue sky with some clouds".

So the published schema ("image_url: string, 图片 URL 或 base64") is right, pi
needs no payload rewrite, and the object form is the dangerous one — a 200 that
loses the input. `live/check.ts` now encodes a real PNG and asserts the image is
actually seen (`input_tokens > 20`).

## Streaming, tools, replay

Event names observed for a completed response (all handled by pi-ai's shared
responses parser): `response.created`, `response.in_progress`,
`response.output_item.added`, `response.content_part.added`,
`response.reasoning_text.delta`, `response.reasoning_text.done`,
`response.content_part.done`, `response.output_item.done`,
`response.output_text.delta`, `response.output_text.done`,
`response.function_call_arguments.delta`, `response.function_call_arguments.done`,
`response.completed` (and `response.incomplete` with
`incomplete_details.reason: "max_output_tokens"` when the budget runs out).
No `data: [DONE]` on this surface, as documented.

Reasoning items come back as
`{type:"reasoning", id:"rs_…", content:[{type:"reasoning_text",text:"…"}], encrypted_content:null, summary:[]}`.
pi stores the whole item as the thinking block's signature and pushes it back
verbatim on the next turn (`openai-responses-shared.js:178`), which the gateway
accepts (probed, and exercised by a real 3-turn tool session). Message ids come
back as `msg_…` and pi keeps them in `textSignature` for replay.

Tool round trip: `output: [reasoning, message, function_call]` with
`{arguments, call_id, id:"fc_…", name, status:"completed"}`; replaying the item
plus `{type:"function_call_output", call_id, output}` returns a completed
message. `parallel_tool_calls: true` appears in responses; pi does not send it.

Fields pi sends that the spec does not define — `reasoning.summary:"auto"`,
`include:["reasoning.encrypted_content"]` — are accepted and ignored
(`encrypted_content` always comes back null, `summary` always `[]`). Left alone:
there is no compat flag for either, and stripping them via `onPayload` would add
risk without changing behaviour.

## Cache on Responses

Same implicit cache, reported as `usage.input_tokens_details.cached_tokens`
(pi maps it to `cacheRead`, verified through the adapter with a recorded stream:
`input_tokens 10, cached 4` → `input 6, cacheRead 4`). Free-model prefix probe:
849 prompt tokens → `cached 4`, then `847`, then `848/848` with
`prompt_cache_key` set. In a real pi session (3 turns, tools): Responses
`44 → 1166 → 1246` cached, completions `405 → 1230 → 1309` — both reach ~98 %
by turn two, so `prompt_cache_key` was not measurably decisive in that scenario;
it is documented as cluster routing and should matter more under load.

## Cost of this round

Every availability/cap/limit probe was a rejection (not billed). Accepted calls:
~30 on free models (¥0) and ~20 on KEY6 at `max_output_tokens` 16-400 with
10-30-token prompts — the GLM-4.7 effort sweep is the bulk of it, roughly
2 000 output tokens at ¥14/M ≈ ¥0.03. Round total ≈ ¥0.05.
